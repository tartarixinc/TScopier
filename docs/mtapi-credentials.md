# MTAPI and broker credential secrets

Plain-English map of every secret that touches MTAPI broker passwords — what it is, where it lives, and what breaks if it is wrong.

---

## 1. `BROKER_CREDENTIALS_ENCRYPTION_KEY` (Supabase + Railway)

**What it is:** A 32-byte secret (usually 64 hex chars from `openssl rand -hex 32`) used as an **AES-256-GCM key** to encrypt the user’s MetaTrader password **before** it is stored in the database.

**Where it lives:**

| Place | Why |
|-------|-----|
| Supabase Edge secrets | `mtapi-broker` / `fxsocket-broker` call `encryptMtPassword()` on **connect** / **reconnect** |
| Railway worker env | Worker calls `decryptMtPassword()` when it runs `ConnectEx` to open a terminal session |

**Format of stored value:** `v1:<iv-b64>:<ciphertext-b64>` in column `broker_accounts.broker_password_encrypted`.

**If missing on Edge:** `isEncryptionConfigured()` is false → `encryptMtPasswordRequired()` throws `ENCRYPTION_NOT_CONFIGURED` and the edge returns **503** before anything is written. The code **fails closed** — no plaintext is ever stored. This is the intended behaviour (verified in `supabase/functions/_shared/brokerCredentialsCrypto.ts`).

**If missing on Worker:** decrypt returns `null` → session manager cannot call `ConnectEx` → account stays disconnected.

**If key changes without re-encrypting rows:** old ciphertext cannot be decrypted → reconnect required for every linked MTAPI account.

**Same value must be used on Edge and Worker** (identical string). Aliases also accepted: `BROKER_CREDENTIALS_KEY`, `MT_PASSWORD_ENCRYPTION_KEY`.

**Code:** `supabase/functions/_shared/brokerCredentialsCrypto.ts`, `worker/src/brokerCredentialsCrypto.ts`.

**Not the same as** the redactor or the nginx API key — this only protects **data at rest** in Postgres.

## 2. `MTAPI_BASE_URL` (Supabase Edge + Railway Worker)

**What it is:** Base HTTPS URL of **our** MTAPI bridge, e.g. `https://mtapi.tscopier.ai`.

**Used for:**

| Caller | Operations |
|--------|------------|
| Edge `mtapi-broker` | `trades`, `opened_orders`, `order_history`, `position_history`, `refresh_summary` (AccountSummary) |
| Worker `mtapiProvider` / `mtapiSessionManager` | `ConnectEx`, `ConnectByToken`, order send/modify/close, health |

Optional platform-specific overrides: `MTAPI_MT4_BASE_URL`, `MTAPI_MT5_BASE_URL` (worker and edge client prefer these if set).

**If missing on Edge:** `isMtapiConfigured()` fails → edge returns  
`MTAPI is not configured. Set MTAPI_BASE_URL in Supabase Edge secrets.`  
Trades/history for MTAPI accounts will not load from the UI path that hits this edge.

**If missing on Worker:** `MtapiApiError: MTAPI base URL is not configured` → no sessions, no trading.

**Port note:** Public entry is **9443** via nginx (`mtapi.tscopier.ai`), not raw `:8080`. Bind the container to `127.0.0.1:8080` (`HOST_IP` default in `install.sh`). UFW cannot block Docker-published ports.

## 3. `MTAPI_API_KEY` (and alias `MTAPI_PROXY_KEY`)

**What it is:** Shared secret that nginx on the VPS expects on every request:

```http
Authorization: Bearer <MTAPI_API_KEY>
```

Generated on the VPS by `docs/nginx-setup/setup.sh` and saved as `/root/.mtapi_api_key`.

**Where it must be set (same string everywhere):**

| Place | Client |
|-------|--------|
| Railway worker env | `mtapiProvider` sets `Authorization: Bearer …` |
| Supabase Edge secrets | `mtapiClient.ts` uses `MTAPI_PROXY_KEY` \|\| `MTAPI_API_KEY` |
| nginx config | `auth_request` / `if` / `proxy_set_header` compares Bearer value |

**If wrong/missing on Edge or Worker:** nginx returns **401/403** on every MTAPI call → trades, connect, summary all fail at the proxy (not a TLS issue).

**If missing on nginx:** either open (bad) or all clients rejected — setup.sh always installs a key.

**Not stored in the repo.** Never commit `/root/.mtapi_api_key`.

## 4. `MTAPI_INTERNAL_TOKEN` (Supabase Edge + Railway Worker + nginx)

**What it is:** Shared secret sent as the `X-Internal-Token` HTTP header on every MTAPI request from the edge and the worker. nginx compares it against the expected value before proxying. It **replaces the IP allowlist**, which broke live traffic on 2026-09-24 when Railway egress rotated (`152.55.177.10` → `152.55.177.237`) and Supabase edge used AWS IPs.

**Where it must be set (same string everywhere):**

| Place | Client / check |
|-------|----------------|
| Supabase Edge secrets | `mtapiClient.ts` sets `X-Internal-Token` when `MTAPI_INTERNAL_TOKEN` is set |
| Railway worker env | `mtapiProvider.ts` sets `X-Internal-Token` when `MTAPI_INTERNAL_TOKEN` is set |
| nginx config | `map $http_x_internal_token $internal_ok` compares the header; `location /` returns 403 if `$internal_ok = 0` |
| VPS file | `/root/.mtapi_internal_token` (generated by `setup.sh`, never committed) |

**If missing on Edge or Worker:** the header is omitted → nginx returns **403** on every MTAPI call (same symptom as a bad IP allowlist).

**If empty on nginx at render time:** the map key becomes `""` and a request **without** the header is **accepted** (fail-open). `setup.sh` refuses to render an empty token and asserts the rendered config has no `"" 1` keys — never leave `/root/.mtapi_internal_token` empty.

**Deploy order (critical):** set the secret on Supabase + Railway and deploy edge/worker **first**, then enable the nginx token check and disable the IP allowlist. Enabling nginx first 403s everything.

**Not stored in the repo.** Never commit `/root/.mtapi_internal_token`.

## Quick matrix

| Secret | Encrypts / authorizes | Edge | Worker | nginx | VPS container |
|--------|----------------------|------|--------|-------|---------------|
| `BROKER_CREDENTIALS_ENCRYPTION_KEY` | Password at rest (AES-GCM) | ✓ encrypt | ✓ decrypt | — | — |
| `MTAPI_BASE_URL` | Route to bridge | ✓ | ✓ | — | — |
| `MTAPI_API_KEY` / `MTAPI_PROXY_KEY` | Bearer auth to bridge | ✓ | ✓ | ✓ checks | — |
| `MTAPI_INTERNAL_TOKEN` | `X-Internal-Token` (replaces IP allowlist) | ✓ sends | ✓ sends | ✓ checks | — |
| Docker log redactor | Stops password in **logs** | — | — | — | ✓ entrypoint |
| nginx `mtapi_safe` log format | Stops password in **access logs** (query string) | — | — | ✓ | — |

## Current status (migration project `supmsgcubipmmowrzoub`)

| Secret | Edge (Supabase) | Notes |
|--------|-----------------|-------|
| `BROKER_CREDENTIALS_ENCRYPTION_KEY` | Present | Required for encrypted connect |
| `MTAPI_BASE_URL` | **Must set** | Needed for new trades/refresh_summary actions |
| `MTAPI_API_KEY` | **Must set** | Same value as `/root/.mtapi_api_key` on VPS |
| `MTAPI_INTERNAL_TOKEN` | **Must set** | Same value as `/root/.mtapi_internal_token` on VPS |

Set from a Supabase token with **secrets write** permission (account owner / service role project token):

```bash
supabase secrets set \
  MTAPI_BASE_URL=https://mtapi.tscopier.ai:9443 \
  MTAPI_API_KEY="$(cat /root/.mtapi_api_key)" \
  MTAPI_INTERNAL_TOKEN="$(cat /root/.mtapi_internal_token)" \
  --project-ref supmsgcubipmmowrzoub
```

(Run the `cat` on the VPS; paste the key into the command on a machine that has Supabase CLI login with secrets access.)

Worker already needs `MTAPI_BASE_URL` + `MTAPI_API_KEY` + `MTAPI_INTERNAL_TOKEN` + `BROKER_CREDENTIALS_ENCRYPTION_KEY` in Railway.

## Relationship to the password-in-logs incident

| Control | Stops password in… |
|---------|-------------------|
| AES key | Database dumps |
| nginx redacted access log | HTTP access logs (query strings) |
| **Log redactor entrypoint** | **Docker container logs (stdout)** |
| API key | Unauthorized callers (not logs) |
| Password rotation | Usefulness of any leaked copy |

All five are complementary; none alone is “done.”
