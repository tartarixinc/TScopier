1. Executive summary (plain English)

We compared how fast the same user’s trades open on the staging environment versus the migration environment. Entry speed is essentially the same on both — about 5 to 6 seconds from the moment a signal is received until the trade appears filled. Migration is not slower; on the raw broker HTTP send it is slightly faster. Separately, migration repeatedly tried (and failed) to fix a stop-loss that did not match the broker. The real problem was that the background “fix the stop” job kept retrying a trade the broker no longer listed as open, instead of closing our leftover open record. That is a sync/cleanup bug on the MTAPI path, not a copy-speed problem; the code fix is written and awaiting deploy.

Root cause found — migration SL-drift loop (460 failed ticks, 04:07–09:07 UTC): On the MTAPI path the V1 basket reconcile monitor kept retrying two XAUUSD baskets (1fcca2ff and 5260104c) after the broker ticket was missing from /OpenedOrders. Legs were skipped as skipped_not_on_broker (not a hard broker error), but the post-pass still compared the database stop against the freshly resolved channel target and logged Reconcile: 0/1 legs; broker SL still drifted every ~70 seconds. An empty OpenedOrders snapshot (session flake) was treated as “nothing open,” which forced every leg down that path. Unlike the merge-refresh and V2 loops, the V1 monitor never closed ghost legs and never treated an empty snapshot as inconclusive — so it retried an impossible modify until the trade was closed elsewhere (1fcca2ff closed 09:07:42) or a later snapshot recovered (5260104c success 08:28). Fix: empty snapshot → release job as inconclusive; all legs missing from a non-empty snapshot → closeStaleOpenTrades + mark job done; failure message now includes “N not on broker”. See scratchpad docs/scratchpad-zejaymes-migration-sl-drift-2026-09-24.md.
