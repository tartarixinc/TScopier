1. Executive summary (plain English): The copier keeps a permanent connection to Telegram for every user, and behind each connection a small background routine pings Telegram to keep the line alive. When a ping fails, Telegram's own library prints an error — and because we had only disconnected the connection instead of tearing it down, that ping routine kept running against a dead line, forever, for every connection we had ever used. In production this produced hundreds of error stacks per minute (about 10–15% of all log output) for at least four days.

On 29 September at 20:57 UTC a large group of connections failed at the same moment: 43 sessions tried to reconnect within a single second, the log service hit its rate limit and started dropping messages, and the worker container restarted about four minutes later (21:01–21:04 UTC). It was not a deployment — the last deployment had been 10.6 hours earlier.

For users this meant hours of growing staleness before the storm (up to roughly two hours), a few minutes of downtime around the restart, and one Telegram session that could not be repaired at all — that user must re-link Telegram. After the restart the listener was dispatching signals again at 22:03–22:09 UTC.

The fix tears down dead connections properly, reacts to every ping timeout instead of ignoring them, spaces out reconnects so a mass failure cannot stampede, and stops retrying forever when Telegram has revoked a login key — it tells the user to re-link instead.

4. Root cause

  1. Orphaned background ping loops. The library's update loop runs while (!client._destroyed) and only exits when destroy() has been called; disconnect() does not set that flag and does not stop the loop (verified in worker/node_modules/telegram/client/updates.js and telegramBaseClient.js). The worker only ever called disconnect() — in stop(), in forceReconnect() and in the recovery paths — and never destroy(). The library's own fallback (client._sender.reconnect()) was patched to a no-op by buildClient() whenever autoReconnect: false, so the loop could not recover either. Every client that had ever been connected kept pinging a dead socket for the life of the process: ~2 stacks/minute each (backtest runs were hit hardest — 560 stacks / 10 min, listener 375 / 10 min).
  2. The timeout handler was skipped in the exact situation it exists for. The handler was guarded with msg.includes('TIMEOUT') && this.isConnected. When a connection stalls, isConnected is already false, so no reconnect was requested and nothing was logged by us — only the library's raw stack. That guard was introduced by commit 4a0febe06 (2026-07-28), replacing the correct guard added on 2026-07-24 (docs/PROJECT_MEMORY.md:2069), and the await on the reconnect was dropped at the same time, so recovery raced the still-running ping loop.
  3. Simultaneous failure → stampede. When many sessions lost their connection in the same second, all 43 requested a reconnect at once with a fixed delay and no jitter: 291 log lines in one second, saturating the 500/s log pipeline.
  4. A revoked key is unrecoverable. 401 AUTH_KEY_UNREGISTERED cannot be fixed by reconnecting, so the watchdog retried every ~30 s forever without telling the user anything actionable.
  5. What restarted the container at ~21:01Z is still unknown — no deployment was in progress and the token cannot read exit metrics.

5. The fix

  1. React to every update-loop timeout. The handler now recognises the ping timeout by message alone (no isConnected guard) and awaits the full reconnect cycle, so the ping loop and the recovery no longer race.
  2. Tear connections down properly. destroy() is now called when a listener stops and when a recovery replaces its client (with a bounded disconnect() fallback), and ephemeral backtest clients are destroyed in a finally. A client that will be reused is still reconnected rather than destroyed, because the library starts its update loop only once per client.
  3. Space out reconnects. The reconnect delay carries a random jitter (TELEGRAM_RECONNECT_JITTER_MAX_MS, default 2000 ms, clamped 0–30 000), so a mass failure spreads across a second or two instead of landing in one tick.
  4. Stop retrying a revoked key. A sessionRevoked flag is set the moment Telegram reports the key as unregistered — from the watchdog, a reconnect cycle, or a duplicated-key recovery. It short-circuits every reconnect path, destroys the client, keeps the lease without the hard-reset cycle that made the re-link banner flicker, and writes telegram_account_status = reconnect_required with recovery_exhausted = true (the existing re-link banner). Callers get a plain error: "Telegram connection expired. Reconnect Telegram to resume copying."
  5. Stop the log flood. The raw Error: TIMEOUT stacks are aggregated to one line per minute (both console.log and console.error are patched at startup, before the Sentry pipeline initialises), and /Error: TIMEOUT\b/ was added to Sentry's log-noise filter. Our own actionable line [userListener] _updateLoop TIMEOUT for <user> — requesting reconnect does not match the pattern and is preserved.
  6. Config safety. A shared envNumber() helper now parses the clamped numeric settings (reconnect cooldown, jitter, connect timeout, auth-duplicate delays, healing ticks). A malformed value used to produce NaN, which silently disables the arithmetic it sits in — a typo in .env could have removed a cooldown or a timeout entirely.

9. Follow-ups

  1. Log export limits: the Railway token used for the investigation cannot read metrics or deploymentLogs, so the 21:01Z restart has no exit reason. A broader read-only token (or the Railway dashboard) is needed to close this.
  2. Separate defect found during the investigation: the per-channel config heal path fails with null value in column "copy_limit_state" (32 occurrences / 10 min, 8 distinct channels), silently defeating "heal missing config from defaults". Not fixed here.
  3. Separate defect found during the investigation: two broker accounts (48b2cdfa-…, 87383068-…) are offline in FxSocket — 104 quote failures each per 10 min, 498 + 335 deferred ghost closes, and 322 OrderModify retries against one permanently rejected ticket with no backoff. Not fixed here.
  4. Alerting: consider an alert on the aggregated update-loop timeout rate (now one line per minute) so a recurrence is visible before it becomes a storm.
