# Broker credential key rotation — runbook

**Scope:** replace `BROKER_CREDENTIALS_ENCRYPTION_KEY` without asking any customer to re-enter a broker password.
**Status:** in progress — staging first, then Unicopier, then production.
**Companion incident record:** `docs/incidents/incident-2026-10-22-railway-env-breach.md`.

## 1. Why a plain key swap is not possible

Every stored broker secret lives in `broker_accounts.*_encrypted` as
`v1:<iv>:<ciphertext+tag>`, sealed with AES-256-GCM. The ciphertext opens only
with the exact key that sealed it; there is no recovery path. Replacing the key
outright would turn every saved broker password into unusable data.

The switch is therefore a **migration**, not a replacement.

## 2. How the migration works

Two key slots are read, one is written:

| Variable | Role |
|---|---|
| `BROKER_CREDENTIALS_ENCRYPTION_KEY` | Primary. Encrypts every new value. Tried first on read. |
| `BROKER_CREDENTIALS_ENCRYPTION_KEY_PREVIOUS` | Previous key(s), comma-separated. **Decrypt-only.** Tried after the primary. |

While both are set, old and new ciphertext are readable, so there is no
downtime and no user action. A diagnostic
(`worker/src/diagnostics/reencryptBrokerCredentials.ts`) then rewrites every
value that was opened by a previous key under the primary, and only after it
reports `on-previous=0` with no failures is the previous key removed.

## 4. Preconditions

1. Deploy the dual-key code **before** changing any key value. Old code ignores
   `PREVIOUS`.
2. Set the new value **and** the old value together on each service. A service
   with only the new key cannot read existing rows; a service with only the old
   key cannot read values written by a service that already has the new key.
3. Know the *current* key of each environment. Staging, Unicopier and production
   may not share one.
4. Have the environment's `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` ready
   for the reencrypt run. The tool refuses to report success on an empty scan,
   so a wrong project is visible.

## 5. Phase 1 — staging

1. **Railway staging**, listener and trade worker:
   - `BROKER_CREDENTIALS_ENCRYPTION_KEY` = new key
   - `BROKER_CREDENTIALS_ENCRYPTION_KEY_PREVIOUS` = staging's current key
2. Deploy `staging`. Worker must start cleanly.
3. **Edge:** set the same two secrets on the staging project (`axdcled…`) and
   redeploy `mtapi-broker` (harmless if secrets are already live).
4. **Smoke:** connect one broker account. A successful connect proves old
   ciphertext still opens through `PREVIOUS`.
5. **Dry-run** against the staging database:

   ```bash
   cd worker
   SUPABASE_URL=<staging url> \
   SUPABASE_SERVICE_ROLE_KEY=<staging service role> \
   BROKER_CREDENTIALS_ENCRYPTION_KEY=<new> \
   BROKER_CREDENTIALS_ENCRYPTION_KEY_PREVIOUS=<old> \
   npm run reencrypt-credentials
   ```

   Check all four lines of the report:
   - `target=` is the staging host;
   - `primary-fingerprint=` matches `f483c14809a4b0ba`;
   - `on-previous=` equals the number of values that exist;
   - no `FAILED` block, `skipped-non-v1=0`.

6. **Apply**, then re-run:

   ```bash
   npm run reencrypt-credentials -- --apply
   npm run reencrypt-credentials            # must print on-previous=0
   ```

7. **Retire the old key:** delete `…_PREVIOUS` from Railway staging and the
   staging edge secrets, redeploy, connect a broker again. If the second dry-run
   shows `on-previous=0`, this is safe.
8. Keep the old key archived offline until the whole incident is closed; do not
   destroy it outright.

## 6. Phase 2 — Unicopier

## 8. What is automatic and what is not

| Action | Automatic? |
|---|---|
| New passwords encrypted with the new key | Yes, once the primary is set |
| Old values still decrypted | Yes, while `PREVIOUS` is present |
| Existing rows moved to the new key | **No** — requires the `--apply` run |
| Old key retirement | **No** — deliberate deletion after `on-previous=0` |

## 9. Safeguards in the diagnostic

- Dry-run by default; writes only with `--apply`.
- Paginates `broker_accounts` in ordered pages, so no account is skipped.
- Reports which key opened each value; values already on the primary are not
  rewritten, so repeated runs are idempotent.
- Compare-and-swap writes: a password changed during the run is never overwritten.
- Undecryptable values are reported and left untouched; the run exits non-zero.
- Unrecognised (`non-v1`) values block the success signal.
- Prints the target host and key fingerprints, and refuses to report success on
  an empty scan unless `--allow-empty` is passed.
- No plaintext, key material or env values are logged.

## 10. Failure handling and rollback

| Situation | Action |
|---|---|
| Dry-run shows `on-previous` lower than expected | Wrong `PREVIOUS` value; stop, correct it, re-run. Nothing was written. |
| Dry-run shows `FAILED` entries | Do not apply. Check the previous-key list against the environment's history. |
| Run stops midway | Database is mixed but valid: both keys are present. Re-run; already-migrated values are skipped. |
| A service was missed | It still has the old key and cannot read values written under the new key. Set both keys on it and redeploy; do not delete `PREVIOUS` until it is current. |
| `PREVIOUS` deleted too early | Old-key ciphertext is unreadable by services that only hold the new key. Restore the old key as `PREVIOUS`, redeploy, rerun the diagnostic. The keys are not destroyed, so this is recoverable. |

## 11. Supabase service keys (separate rotation)

This is independent of the broker key and does not interact with it.

- **What rotates:** the project JWT signing secret (which invalidates the
  `service_role` and `anon` JWTs) or the newer publishable/secret API keys.
- **Consumers:** edge functions (values are injected by the project), Railway
  workers (`SUPABASE_SERVICE_ROLE_KEY`), the frontend (`VITE_SUPABASE_ANON_KEY`,
  baked at build time — requires a Netlify rebuild), and any external
  integration holding a copy.
- **Order:** generate new keys → update Railway and external consumers → rebuild
  and deploy the frontend with the new public key → disable the old keys.
- **Consequence to plan for:** rotating the JWT secret logs every user out.
  Publishable/secret keys can coexist with the legacy JWT and avoid that.
- **Verification:** sign-in, one edge-function call, one worker database write,
  one storage upload.
